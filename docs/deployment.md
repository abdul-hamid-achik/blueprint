# Deployment

Blueprint's supported deployment artifact is the Docker image generated by the
Node target. The image is a normal OCI container: build it locally or in CI,
push it to your registry, and run it on any container platform.

This guide deliberately does not provide serverless adapter recipes. Generated
Node output starts a long-running Hono server; adapting it to a function runtime
requires a separate, tested entrypoint that Blueprint does not generate today.

## What Blueprint generates

```bash
bp build service.bp --target node --out generated
```

The output includes a multi-stage `Dockerfile` that:

- installs dependencies and compiles TypeScript in a builder stage
- installs production dependencies in the runtime stage
- copies only `dist/` into the runtime image
- runs as a non-root `app` user
- exposes the port declared in the Blueprint block
- starts with `bun dist/index.js`

The Node app also exposes `GET /health` automatically. It returns process
status and uptime and is intended as a liveness probe. Do not add another
`GET /health` route. If traffic should wait for PostgreSQL, Redis, or another
dependency, add a separate application-specific readiness endpoint.

See [Generated Output](/generated-output) for the rest of the project layout.

## Build and run the image

Assume `service.bp` declares port `8080`:

```bash
bp check service.bp
bp build service.bp --target node --out generated

docker build -t registry.example.com/team/service:1.4.0 generated
docker run --rm \
  --name service \
  --env-file production.env \
  -p 8080:8080 \
  registry.example.com/team/service:1.4.0
```

Probe the built-in liveness route from another terminal:

```bash
curl --fail http://localhost:8080/health
# {"status":"ok","uptime":...}
```

The declared Blueprint port is compiled into the server and written to the
Dockerfile's `EXPOSE` instruction. A runtime `PORT` environment variable does
not currently override it. Configure the container platform to use that port,
or change the Blueprint and rebuild.

Use immutable image tags in production. Push and roll out the image with your
registry and container platform's normal tooling; `bp` does not perform those
remote operations.

## `bp deploy`: local build and smoke test

`bp deploy` is a convenience command around the Node build and local Docker
build:

```bash
bp deploy service.bp \
  --target docker \
  --out generated \
  --tag registry.example.com/team/service:1.4.0
```

It performs these steps:

1. Builds the **Node** target into the output directory.
2. Runs `docker build` for that directory.
3. Starts a temporary container named `bp-smoke`.
4. Probes `GET /health` from inside the container.
5. Removes the temporary container.

This verifies a local image; it is not a remote deployment. It does not push to
a registry, create infrastructure, or keep the container running.

### Current `bp deploy` limitations

- `--target` is a deployment target, not a codegen target. Only `docker` works;
  `fly` is reserved but returns a not-implemented error.
- It always generates the Node target. Python and Effect output are not wired to
  `bp deploy`.
- The smoke test maps and probes the port declared by the generated Dockerfile.
  It does not currently support a different host-side port.
- The temporary container receives no `--env-file` or secret flags. A service
  with required secrets, PostgreSQL, Redis, workers, or schedules can fail its
  smoke start even when the image is valid. Use `--no-run` and run the image
  with representative runtime configuration.
- The output directory must be fresh/empty or already owned by Blueprint through
  `.blueprint/manifest.json`; `bp deploy` does not expose `--force`.

CI commonly uses:

```bash
bp deploy service.bp \
  --target docker \
  --out generated \
  --tag registry.example.com/team/service:${GIT_SHA} \
  --no-run

# Push with your registry tooling after the build succeeds.
docker push registry.example.com/team/service:${GIT_SHA}
```

For a configured smoke test, run the resulting image explicitly with
`--env-file`, the declared port, and access to disposable dependencies.

## Runtime configuration and secrets

Every build emits `.env.example` from declared `secret` and `env` values. Treat
it as a schema/template, not as a production secret file.

```bash
cp generated/.env.example production.env
# Fill production.env using values from your secret manager.
```

Inject values at container runtime with your platform's secret store or an
environment file:

```bash
docker run --env-file production.env -p 8080:8080 service:1.4.0
```

Required secrets fail validation during application startup. Database, queue,
cache, schedule, and multi-instance realtime features may also require
`DATABASE_URL` or `REDIS_URL`; inspect the generated `.env.example` for the
exact build.

Do not commit production values or bake them into the image. The generated
`.gitignore` excludes `.env`, but Docker sends its build context independently.
Add a `.dockerignore` to the generated build context or maintain one in your
deployment wrapper, for example:

```text
.env
.env.*
!.env.example
node_modules
dist
.git
```

## Database migrations

Run migrations once per release, as a separate job before new replicas receive
traffic. Do not have every application replica race to migrate on startup.

### Node: Drizzle Kit

For development, `push` synchronizes the schema directly without creating a
versioned migration:

```bash
bp migrate service.bp push --target node --out generated
```

For production, generate and review migration files during development or CI:

```bash
bp migrate service.bp generate --target node --out generated
bp migrate service.bp check --target node --out generated
```

Persist the resulting `generated/drizzle/` files with the release artifact.
Apply reviewed migrations from the generated project in a one-shot release job:

```bash
cd generated
DATABASE_URL='postgresql://...' bunx drizzle-kit migrate
```

`bp migrate ... studio` is a local inspection tool, not a production migration
step.

### Python: Alembic

The Python target uses `uv` and Alembic instead of Drizzle Kit:

```bash
# Create an autogenerate revision.
bp migrate service.bp generate --target python --out generated-python

# Verify model changes are represented by migrations.
bp migrate service.bp check --target python --out generated-python

# Apply all pending revisions (alembic upgrade head).
bp migrate service.bp push --target python --out generated-python
```

`studio` is rejected for Python because Alembic has no equivalent GUI. The
Effect scaffold has no migration integration.

Blueprint does not currently generate a Dockerfile for the Python target, and
`bp deploy` cannot package it. If you containerize Python output, keep that
Dockerfile under your own deployment ownership and run the generated app with
the Blueprint-declared port, for example via `uv run uvicorn src.app:app`.

See [CLI Reference](/cli-reference) for the full migration command surface.

## Generated files and deployment customization

`.blueprint/manifest.json` records files owned by the generator. On rebuild,
Blueprint can replace generated files and remove stale ones; it warns when a
tracked file has been hand-edited.

Do not customize the generated Dockerfile in place and assume the edit will
survive. Choose one of these approaches:

- keep an organization-specific Dockerfile, Compose file, or platform manifest
  outside the generated output and point it at the generated build context
- make target-language changes in scaffolds marked `UserOwned` (such as native
  implementation and save-migration stubs), which Blueprint creates once and
  preserves
- run `bp eject generated` when you intentionally want to stop regenerating and
  own the entire project

After ejecting, a later `bp build` treats the directory as foreign and refuses
to overwrite it unless explicitly forced.

## Multi-instance and security caveats

Generated code is a starting point, not an infrastructure security boundary.
Review these behaviors before scaling beyond one process:

- Bare metadata such as `auth api_key`, `auth bearer`, or `auth session` does
  not generate generic credential verification on Node. Use explicit,
  tested middleware. Generated webhook HMAC verification is the implemented
  exception.
- Endpoint `cache <duration>` is currently metadata only; it does not cache
  responses.
- Endpoint rate limits use an in-process map. Every replica has its own counter,
  and the generated code trusts `X-Forwarded-For`. Use a trusted proxy plus a
  gateway or distributed limiter for production enforcement.
- `emit` and ordinary subscriptions are process-local. Use BullMQ `enqueue` for
  distributed worker jobs. Configure and test Redis-backed realtime behavior
  before relying on cross-replica WebSocket delivery.
- `/health` proves that the process can answer HTTP; it does not prove that the
  database, Redis, object storage, or downstream APIs are ready.
- Every replica creates its own database/Redis connections. Size pools and
  deployment concurrency together.
- WebSocket services require a proxy/load balancer that preserves upgrade
  headers and has appropriate idle timeouts.

## Production checklist

Before routing production traffic:

- [ ] Pin the `bp` version used by CI and keep the `.bp` source under review.
- [ ] Run `bp check`, relevant generated tests, and a target-language build.
- [ ] Build an immutable image and scan its dependencies and filesystem.
- [ ] Inject every required secret at runtime; keep values out of source,
      images, logs, and CI output.
- [ ] Generate, review, back up, and apply database migrations once per release.
- [ ] Match the container port to the Blueprint-declared port.
- [ ] Configure `/health` as liveness and a dependency-aware route as readiness
      when required.
- [ ] Implement and test real authentication/authorization middleware.
- [ ] Put distributed rate limiting, request-size limits, TLS, and trusted proxy
      handling at an appropriate edge layer.
- [ ] Restrict CORS to intended origins and verify error responses do not expose
      secrets or internal stack traces.
- [ ] Send stdout/stderr to centralized logs and add metrics/tracing outside the
      generated defaults.
- [ ] Verify graceful termination, database pool sizing, Redis availability,
      worker/schedule behavior, WebSocket upgrades, and rollback procedures.
- [ ] Test backup restoration and the previous image/migration rollback plan.

For generated test behavior before release, see [Testing Guide](/testing-guide).
